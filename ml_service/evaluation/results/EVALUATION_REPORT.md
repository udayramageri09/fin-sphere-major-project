# FinSphere ML evaluation report

Generated by `python -m ml_service.evaluation.run_evaluation` (Python 3.12.10, numpy 2.4.2, pandas 3.0.2, scikit-learn 1.8.0).
Every number below is computed by that run from deterministic synthetic fixtures; nothing is typed in by hand. No real user data is used.

## 1. What is actually machine learning here

| Component | Type | Algorithm | Persisted model / dataset |
|---|---|---|---|
| forecaster | statistical model fitted per request (ordinary least squares, supervised regression) | sklearn LinearRegression of monthly income and of monthly net spending on a month index, fitted separately | none persisted: it is re-fitted on the user's history on every request; no model file, no dataset |
| anomaly_detector | trained unsupervised ML, fitted per request (transductive: it scores the same rows it is fitted on) | sklearn IsolationForest (100 trees) on StandardScaler-scaled [abs_amount, day_of_week, day_of_month] | none persisted |
| clustering | unsupervised ML fitted per request | sklearn AgglomerativeClustering, Ward linkage, k fixed at 3, on StandardScaler-scaled [abs_amount, is_expense] | none persisted |
| health_scorer | heuristic / deterministic rule system (no learning) | six ratios scored 0-100 by piecewise-linear benchmark curves and combined with fixed weights; weights renormalised over available ratios | none |
| plan_generator | heuristic / deterministic rule engine (no learning) | if/else threshold rules over the outputs of the four components above | none |

Notes found during the audit:

- **forecaster**: the month index is the position among months that HAVE transactions, so a missing calendar month is collapsed (see the missing_months benchmark)
- **forecaster**: R2 is in-sample, not a held-out accuracy
- **anomaly_detector**: contamination = min(0.15, max(1/n, 0.05)): it ALWAYS flags a fixed share (>= 5%, >= 1 row) of the rows, even in a clean dataset
- **anomaly_detector**: no fraud labels exist, so detection quality can only be measured on synthetic injected anomalies
- **clustering**: k is not selected from the data: it is always 3
- **clustering**: is_expense is constant after filtering, so only the amount drives the clusters
- **clustering**: the plan rules and ML metadata call this "KMeans" although the algorithm is Agglomerative (a naming inconsistency, not a numerical one)
- **health_scorer**: the benchmarks (e.g. savings 20% / 30%, DTI 36%) are conventional rules of thumb, not fitted to data
- **plan_generator**: it is not machine learning; its quality is rule correctness, which is evaluated by boundary and coverage checks

## Key findings (derived from the measured numbers)

- **forecaster** (limitation): The model LOSES to at least one naive baseline on: noisy_stable, seasonal (14 series x target x baseline comparisons). A straight line cannot represent seasonality and over-reacts to noise, where a historical mean does better. Reported as measured; the benchmark was not changed.
- **forecaster** (info): Across all baseline comparisons the model was strictly better 46 times; many comparisons tie (MAE 0 for everyone) on perfectly stable series, where there is nothing to predict.
- **forecaster** (potential_defect): Months with no transactions are collapsed (the regression index counts only months that have data). On an exact linear trend with every third month missing, income MAE is 1151 vs 0 with complete history. Reported only; production code was not changed.
- **forecaster** (info): Classification matters: with refund / transfer rows in the data, spending MAE against the analytical truth is 0 with classification and 24000 when the same rows are unclassified.
- **anomaly_detector** (limitation): Contamination is fixed, so on a CLEAN dataset the detector still flags 5.0% of rows; precision with one injected anomaly is capped near 1 / (rows flagged).
- **anomaly_detector** (limitation): A typical-sized transaction on an unusual day of the month is caught only 60% of the time in the synthetic test (large amounts are caught reliably).
- **clustering** (limitation): On a population with three clearly different spending levels the clusters recover the generating groups only partially (ARI 0.39; replicate-1 cluster sizes [150, 4, 2]). Amounts are standardised linearly, so a few very large expenses dominate the scale and the small and medium groups merge; the silhouette (0.96) is high because of those extreme points, so it overstates quality here.
- **clustering** (limitation): k is fixed at 3: on a homogeneous population with no structure the model still returns 3 clusters (silhouette 0.52).

Edge cases:

- PASS: fewer than 3 spending rows -> empty result with an explanatory message
- PASS: income rows never count toward the minimum
- PASS: nearly identical rows: runs, labels every row, no crash
- PASS: rows differing by a paisa: still partitions deterministically (rerun identical)
- PASS: one extreme outlier forms (or dominates) the high-value cluster: its share of the total is ~ the outlier's
- PASS: transfers, refunds and income are excluded from clustering
- PASS: unknown debit-direction rows are clustered (fallback); unknown credits are not
- PASS: rows without a classification field follow the unknown fallback

Limitations: unsupervised: there are no true labels for real spending; silhouette / ARI are computed on SYNTHETIC populations with known structure; k is hard-coded to 3 (no model selection), so data with 1 or 2 natural groups is still split into 3; clusters are driven by the amount alone (the is_expense feature is constant after filtering).
